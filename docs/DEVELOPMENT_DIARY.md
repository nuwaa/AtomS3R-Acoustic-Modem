# 開発日記 — AtomS3R Acoustic Modem

**日本語** | [繁體中文（臺灣）](DEVELOPMENT_DIARY.zh-TW.md) | [简体中文](DEVELOPMENT_DIARY.zh-CN.md) | [English](DEVELOPMENT_DIARY.en.md)

ATOM S3R + Atomic Echo Base を使った音響TNCの開発記録。日付が確かでない初期作業は「ごろ」と記し、実機で通過した試験と未解決の課題を区別する。10月11日以降のBell 103開発は `feature/bell103` ブランチ上の作業であり、`main` の保存版に実装済みという意味ではない。今後の作業も日付順に末尾へ追記する。

## 2026年10月5日ごろ — 音をデータにする

ATOM S3Rのマイクから取得したPCMとスピーカー出力を調べ、Bell 202の1200bps AFSKでAX.25フレームを送受信する土台を作った。1台で音が出ることと、2台を空中の音でつないでフレームを復号できることは別の課題だった。CRCや波形を見ながら、まず2台での通信を確かめた。

## 2026年10月6〜7日ごろ — USBとIPへ広げる

音響AX.25部分をtransportとして整理し、USB CDC、SLIP、PPPを後から組み合わせられる構造にした。PC間のチャットや連続UDP試験を進め、AndroidをUSB-CでATOMにつなぐアプリも作り始めた。PCとOPPOから文字を送り、音響IPトンネル経由の双方向pingも確認した。日本語・繁体字の表示、Androidのキーボードと送信ボタンの重なりなど、実際に使って初めて分かった問題も直した。

## 2026年10月8日ごろ — グループチャットを試す

PCのチャットサーバーを介さず、ATOM同士で直接チャットする方向へ進めた。将来3台以上に増やすことを意識し、グループ配信と欠落時のSUMMARY/NACKによる回復を実装。COM5・COM6の2台でUTF-8の双方向通信を確認し、PCとOPPOでもチャットとpingを併用できた。ATOMの小画面で読めなかった日本語・カタカナの字形も調整した。

## 2026年10月9〜10日ごろ — Android同士で会話する

2台のAndroid端末をそれぞれATOMへUSB-C接続し、直接チャットが双方向に通った。グループチャットでは過去の電文が後から一気に届く現象があり、保存状態と再送を見直した。アプリはチャットを中心にした画面に整え、不要になった操作ボタンも整理した。将来の3台目でパケットを観測するモニターモードも、実機の到着前に準備した。

## 2026年10月11日 — Bell 103を加える

動作しているBell 202 / AX.25を保存してGitHubリポジトリを作り、MITライセンスと依存関係を整理した。別ブランチでBell 103の300bpsモードを実装。ダイヤルアップ風の接続音から始め、FSK送受信、発呼・応答、接続確認、本文とACK、再送を段階的に試した。Android同士、PCとAndroidの双方で日本語・繁体字が届き、切断後にAX.25へ戻ることも確認した。30分の実機試験では27通すべてが着信・ACKを得て、7回の再送が発生した。

## 2026年10月12日 — 順序と画面ロック中の欠落を追う

通信遮断後の表示順を見直し、Bell 103の受信待ち時間も短縮した。一方、PCで「送達」と表示されても、画面ロック中のAndroidアプリで先行する本文が欠落する事例があった。「送達」は相手ATOMからの音響ACKで、アプリの保存完了ではないと分かった。

そこでATOMに16件の受信箱を追加し、Androidが本文を保存してからUSB側の確認を返すようにした。5分以上の画面ロック中に長文F09→短文F10を送り、アプリで各1回、順番どおりに表示された。アプリを停止したまま送達したR01も、再起動後に1回だけ再取得できた。直接・グループチャットも双方向で通過した。ただし、ATOMの受信箱はRAM上にあり、電源断や17件以上の未確認着信はまだ守れない。

同日の試験では、相手ATOMから音響ACKを得られず送信失敗した試行もあった。これはAndroidへのUSB受け渡しとは別の課題。次は2台の配置を固定し、受信側がフレームを復号できなかったのか、ACKを返せなかったのかをログで切り分ける。

## 2026年10月13日 — Bell 103の待ち時間を測る

Bell 103の受信窓を接続後のみ最大9秒から6秒に短縮し、無音を検出した時の早期復号が失敗しても、新しい信号を受けた後に再試行できるようにした。2台のATOMでビルド・書き込み後、5分試験は15通すべて着信・ACK、再送2回で通過。30分試験も32通すべて各1回着信、ACK32件、再送6回で通過した。

30分ログで、送信指示から本文着信までの中央値は6秒、ACKまで9秒。以前の30分ログではそれぞれ14秒、17秒だった。ただし試験時の音響条件と送信間隔は同一ではないため、厳密な性能比較ではない。接続音は引き続き約11秒で、接続完了は今回約20秒。5分・30分の両試験後、AX.25直接チャットは双方向PASS。

同日、USB送信指示が来たとき、音響信号をまだ検出していない受信処理から早めに戻る試験をした。6秒窓では30分・30通を全数送達したが再送11回、送達中央値7秒だった。9秒窓では29通を全数送達、再送4回、送達中央値8秒。どちらも一方的な改善ではなかった。

受信窓の長さは9秒のまま、直近約0.13秒の平均音量で電文末尾の静音を判断する方式に変更した。短いマイク雑音で静音判定が途切れるのを避け、CRCが正しければ窓の終了前に復号する。5分試験は16通・再送2回、30分試験は32通すべて各1回着信・ACK32件・再送0回でPASS。30分の送達中央値は10秒、ACK中央値は12秒であり、送達時間の短縮が常に得られたわけではない。接続音は変更せず、試験後のAX.25直接チャットも双方向PASS。異なる試験回の数値は音響条件が完全には揃っていないため、参考比較にとどめる。

## 2026年10月18日 — klesis Webチャットの音をATOMで受信する

`feature/ggwave` に、[klesis Webチャット](https://github.com/nolimitwaiz/klesis) の音を受ける専用モードを追加した。既存のATOM間ggwaveチャットは固定長フレームと独自の分割・ACKを使うため、klesisの可変長フレームは別の受信モードで復号する。Android 0.4.3には「Web音声を受信」操作を設け、本文を従来のチャット欄にも表示した。ファームウェアとAndroidアプリはともにビルドPASS。

COM5のATOMでは、klesisのAudible Normalから送った「こんにちは」「你好」「Hello」を実際の空気中の音で復号し、専用試験はPASSした。Web受信終了後、AX.25直接チャットも双方向で本文・送達確認を確認した。COM5のATOMを1台目OPPOへ接続すると、`Web確認 こんにちは` がOPPOのチャット欄とATOM小画面の両方に表示された。

もう1台のATOM（COM6）にも同じファームウェアを書き込み、もう1台のOPPOにも更新アプリを導入した。両方の書き込み・インストールがPASSし、こちらの組でもklesisからの `Web確認 你好` がOPPOとATOM小画面の両方に表示された。今回実機で確認したWeb音声方式はAudible Normal。Fast/Fastest、44.1 kHz環境、超音波方式、ATOMからklesisへの送信は未検証である。Web受信モードは受信専用で、既存のggwaveチャットと同時には使わない。
